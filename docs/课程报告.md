# 基于本地大语言模型的求职材料诊断与模拟面试系统

CareerLens 课程设计报告

日期 2026 年 10 月

## 摘要

本项目设计并实现了一套面向大学生及应届毕业生的求职训练应用 CareerLens。用户在本机导入简历和目标岗位描述，系统提取岗位能力要求，核验简历证据，生成诊断建议，并据此开展多轮文字模拟面试。应用由中文 Web 界面、Python 业务服务、SQLite 数据库、本地检索模块和 Ollama 模型接口组成，目标部署环境为 Linux，运行阶段不依赖云端大模型 API。

系统将简历与岗位之间的对应关系组织为能力证据矩阵。模型负责理解自然语言，服务器负责校验引用、计算证据覆盖分、控制面试状态及保存历史。面试反馈包含六个评分维度、评分理由和具体练习建议。材料更新与历史会话采用版本和快照分离，避免后续修改影响既有训练记录。项目提供可运行源码、Linux 部署脚本、演示材料、自动化测试和 HTML 报告导出。

本次开发环境为 Windows，已识别到 RTX 4050 Laptop 6 GB 显存，但未安装可用的 Linux 子系统和 Ollama。因此，功能验证使用显式规则模式及符合 Ollama 协议的测试服务；这些结果证明业务流程和协议处理的行为，不代表真实模型质量或 Linux GPU 性能。Linux 实机部署和模型质量评估是验收时需要补充的实验。

关键词 本地大语言模型 检索增强生成 简历诊断 模拟面试 Linux

## 1 项目背景与需求分析

### 1.1 应用问题

学生求职准备涉及两个相互关联的问题。一方面，简历通常按课程或项目经历组织，招聘信息则按业务职责和技能要求组织，学生难以判断某项经历究竟能支持哪项岗位要求。另一方面，即使简历写出了技术名称，面试时仍需要解释本人做过什么、为什么这样做、如何验证结果。只有文本润色而没有后续训练，不能完整解决上述问题。

简历和面试回答还包含联系方式、教育背景及个人经历。将应用部署在个人设备上，可以减少材料发送到第三方服务的需要。因此，本项目将本地推理和本地持久化作为基本约束，利用开源模型完成自然语言理解与追问，将训练过程组织成可以回顾的记录。

### 1.2 用户与使用流程

首版面向单个大学生或应届求职者。用户创建求职项目，导入简历并粘贴一份目标岗位描述，保存后生成岗位分析。用户查看每项能力对应的简历引用与缺口，再开启五至十二轮模拟面试。面试可暂停和恢复，完成后查看逐轮反馈并导出报告。

应用不进行自动招聘决策，也不将个人训练分数作为录用概率。缺少材料证据仅说明简历尚未证明某项能力，不能据此断定求职者不会该技能。

### 1.3 功能与运行要求

| 需求类别 | 实现要求 |
| --- | --- |
| 材料管理 | 导入 TXT、DOCX 和文本型 PDF，编辑与保存简历及岗位 |
| 诊断分析 | 提取岗位要求，核验引用，提供可解释的匹配结果和修改建议 |
| 面试训练 | 个性化首题、根据回答追问、六维反馈、暂停恢复 |
| 历史与报告 | 本地保存训练记录，材料版本隔离，生成可打印 HTML 报告 |
| 部署 | Linux 环境启动，默认本机访问，本地模型，静态资源随项目分发 |
| 异常处理 | 文件错误、模型不可达、结构错误、超时和重复提交均有明确提示 |

为控制课程开发范围，首版采用文字面试，未加入语音、视频、数字人或招聘网站自动投递。简历优化以建议和补充问题呈现，用户确认后自行编辑，系统不将未经核实的新事实自动写入简历。

## 2 技术方案与总体设计

### 2.1 总体架构

系统采用浏览器与本地服务分离的结构。浏览器负责材料编辑、结果呈现和面试交互；FastAPI 提供同源接口并提供静态页面；业务服务组织分析与面试流程；SQLite 保存材料和训练数据；Ollama 在本机加载开源模型。业务服务通过 HTTP 调用本机模型接口，不需要向云端提交材料。

前端使用原生 HTML、CSS 和 JavaScript，所有脚本和样式保存在源码目录中，不使用在线 CDN 或外部字体。后端按配置、数据合同、持久化、文件解析、检索、模型接口、业务服务、报告和路由拆分，便于分别验证和维护。

### 2.2 技术选型理由

| 层次 | 选型 | 选择原因 |
| --- | --- | --- |
| 交互界面 | 原生 Web 技术 | 无前端构建依赖，可随 Python 服务离线提供 |
| API 服务 | FastAPI 与 Pydantic | 请求校验、接口文档、结构化结果校验 |
| 持久化 | SQLite | 单用户无需额外数据库服务，支持事务和外键 |
| 文档解析 | pypdf 与 python-docx | 提取 PDF 文本、DOCX 段落与表格 |
| 本地检索 | BM25 | 不需要额外向量模型，适合小规模材料与指南 |
| 模型运行 | Ollama | 通过统一的本机 HTTP 接口调用量化模型 |
| 自动测试 | pytest 与 TestClient | 覆盖 API、业务状态、数据库和异常路径 |

### 2.3 模型与硬件适配

默认模型为 Qwen2.5 3B，以适应约 6 GB 显存的设备。显存较充足时可以通过配置切换到 Qwen2.5 7B。7B 标签对应的量化模型文件约 4.7 GB，但实际显存占用还包括运行时和上下文缓存，不能用文件大小直接推断是否能全部装入 GPU。不同模型规模的许可也需要分别核对。

上下文默认配置为 4096。系统为材料分析、首题生成和回答反馈分别预留 1800、350 和 1000 token 的输出预算。调用前依据中文字符与其他字符数量进行保守输入估算，超预算时要求精简内容或增加上下文，不静默截断原始材料。该方法不是精确分词，仍需通过目标模型实测校准。

### 2.4 两种运行模式

正式模式调用本地 Ollama，服务不可达、缺少模型、超时或结果结构错误时返回失败，并保留原有状态。规则演示模式由用户显式选择，按照预设规则生成确定性结果，用于无模型条件下检查工作流。界面、分析、会话和报告均记录引擎类型，正式模式不会在失败后自动切换到演示模式。

## 3 数据设计与状态管理

### 3.1 数据实体

| 数据实体 | 主要内容 | 关联关系 |
| --- | --- | --- |
| projects | 项目名、简历、岗位、材料版本、当前分析 ID、时间 | 一个项目可有多个分析和会话 |
| analyses | 材料快照、能力要求、引用、诊断、覆盖分、模型与耗时 | 引用所属项目 |
| sessions | 分析 ID、题目、回答、反馈、轮数、状态、版本 | 引用创建时的分析快照 |

SQLite 表保留实体主键及关联字段，将可变结构保存为 JSON。这样可以容纳不同数量的岗位要求与面试轮次，降低课程项目中的迁移成本。代价是复杂统计查询较不方便；若后续扩展到多用户，应把面试轮次与评分拆分为规范化表。

### 3.2 材料版本与快照

每次编辑并保存材料，项目版本加一，当前分析链接清空。新面试必须基于重新生成的当前分析。既有面试保留创建时的分析 ID，因此修改简历不会改变历史题目、证据和报告。

模型推理在数据库事务之外执行，避免长时间阻塞写操作。推理完成后，服务在事务中重新检查材料版本或会话版本；如果记录已被其他请求修改，拒绝覆盖并提示刷新。分析并发提交还会比较原分析 ID，避免相同材料版本的两次请求相互覆盖。

### 3.3 面试状态机

面试具有 active、paused 和 completed 三种状态。active 可以提交回答或暂停；paused 可以恢复，但不能提交答案；达到设定轮数后进入 completed，并不再生成待回答题目。每次提交或状态切换均增加版本，重复请求不能消耗第二次轮次。

浏览器会话中暂存当前答案草稿，暂停和刷新后可以恢复；提交成功后移除该草稿。服务器只保存已经提交的回答。关闭浏览器会话可能清除草稿，因此正式记录以服务器保存的轮次为准。

## 4 核心算法与大模型应用

### 4.1 岗位要求提取

模型接收简历、岗位描述和任务约束，返回符合 JSON Schema 的结构。每项要求包含名称、必需或加分属性、岗位原句及简历证据。材料诊断还包含被诊断原句、问题、改进建议和严重程度。

服务器使用 Pydantic 校验字段类型、长度、数组数量及枚举值。不符合结构的结果不落库。这样能够约束输出形式，但不能证明模型理解正确，语义判断仍需用户复核。

### 4.2 引用核验与证据分级

岗位原句必须是岗位描述的连续子串，简历引用必须是简历的连续子串。服务器剔除无法定位的引文、重复证据和明显否定性表述，并记录验证提醒。如果所有岗位要求都无法定位，整次分析失败，避免生成没有来源的匹配报告。

对通过核验的简历引用，系统使用行动词规则辅助分级。含有开发、实现、测试、组织等行动描述的证据标记为有行动证据；只有技能名称而没有行动描述时标记为仅提及；没有有效引用则标记为缺少证据。界面保留原句与字符位置，用户可以检查分类是否合理。

这是一种轻量启发式方法。行动词存在并不保证经历充分，否定性识别也不能覆盖所有复杂句法。引用核验的直接价值是可追溯，而不是自动证明候选人经历真实。

### 4.3 岗位证据覆盖分

必需项权重为 2，加分项权重为 1。有行动证据、仅提及和缺少证据分别取 1、0.4 和 0。系统对各项权重与状态值的乘积求和，除以全部权重之和，再乘以 100 并四舍五入。

例如，岗位有两个必需项和一个加分项，证据状态分别为有行动证据、缺少证据、仅提及，则分子为 2 加 0 加 0.4，分母为 5，最终覆盖分为 48。这个分数表达材料对已提取岗位要求的覆盖程度。模型漏提要求或误判权重会影响分数，因此应与完整岗位原文一同查看。

### 4.4 本地检索增强

系统将简历和项目自编的面试训练指南分为短文本片段。英文采用词项，中文采用字符二元组，以 BM25 衡量片段与查询的相关程度。分析结果可展示检索片段；面试阶段根据当前问题与回答检索相关训练方法，再加入生成请求。

个人材料与训练指南具有不同来源标记。完整简历已作为个人事实输入时，不再重复把相同材料塞入提示词，以节省上下文。指南只能支持 STAR 回答方法、项目深挖和训练建议，不能充当用户会某项技能的证据。该方案适合小规模本地文档，对语义近似但词语差异较大的表达识别有限，后续可以加入本地向量检索。

### 4.5 自适应面试与回答评估

首题结合简历和能力状态生成，通常从代表性项目与个人贡献开始。后续请求包含当前问题、本轮答案、最近两轮答案、已经提过的问题以及相关指南。较早答案不再完整加入模型上下文，但仍保存在历史中。这个取舍控制了上下文消耗，也意味着模型可能遗漏较早回答的细节。

每轮反馈包括回答相关性、内容完整性、事实一致性、表达清晰度、STAR 结构及岗位能力六项零至五分。评价规则从没有有效回答到充分且具有验证依据逐级展开，同时要求输出评分理由、亮点、改进项与一项具体练习。页面以逐轮反馈及平均分雷达图呈现结果。

追问应针对模糊行动、缺少结果或能力缺口。服务检查完全重复的题目，出现重复时使用改进与验证问题作为兜底。新增经历只视为待补充信息，不能自动认定虚假，也不会自动回写简历。

## 5 功能实现与界面组织

### 5.1 材料工作台

材料页面支持 TXT、DOCX 和文本型 PDF 导入，并允许用户复核、编辑后保存。TXT 尝试 UTF-8 和 GB18030 解码；DOCX 提取段落与表格；PDF 限制页数并拒绝不支持的加密文档。没有提取到文字时提示用户先做 OCR 或粘贴正文。

单文件上限为 10 MB，DOCX 还检查压缩包展开体积。保存简历最多 5000 字，岗位最多 3000 字。表单上限是材料存储限制，不代表所有最大长度输入都能放入默认模型上下文。原始上传文件在解析后关闭，不保存到磁盘。

### 5.2 分析与训练界面

工作台展示求职项目、训练数量、完成数量和最近训练。诊断页面显示能力矩阵、逐条材料建议、证据覆盖公式及引文校验提醒。用户可以从分析结果进入模拟面试，也可以从训练档案恢复已有会话。

面试页面保留当前题目、问题类别与关注点，提供答案输入、暂停和继续操作。已提交轮次以独立卡片保存问题、原回答、六项评分和理由。平均分仅概括本次训练，不声称不同模型或题目具有一致量尺。

### 5.3 报告导出

服务分别提供材料诊断报告和面试训练报告。报告包含引擎、分析时间、能力矩阵、诊断建议、能力缺口，以及面试原题、答案、反馈和材料快照。HTML 随服务器直接生成，无需额外的在线导出服务。用户可以在浏览器中打印保存为 PDF。

导出前对用户输入及模型内容做 HTML 转义，避免把内容作为网页脚本执行。Web 界面同样通过文本节点呈现动态内容，不把简历和模型输出直接拼成可执行 HTML。

## 6 本地部署与异常处理

### 6.1 Linux 部署方法

目标机准备 Python 3.10 或更高版本、venv、NVIDIA 驱动和 Ollama。在项目目录执行安装脚本创建独立 Python 环境并安装依赖，提前拉取配置中的本地模型，然后执行启动脚本。默认服务监听 127.0.0.1 的 8000 端口，只向本机浏览器提供访问。

项目还提供 Linux host 网络模式的容器配置，以连接宿主机的本地 Ollama。容器首次构建需要基础镜像和依赖；离线安装应先在兼容的联网 Linux 机器准备 wheelhouse、模型和必要安装包，不能把 Windows 虚拟环境直接复制到 Linux 使用。

### 6.2 模型故障处理

健康检查查询本机模型清单，显示模型未安装、服务未启动或已准备就绪等状态。推理请求禁用环境代理，防止本机材料请求绕到代理。Ollama 地址配置仅接受本机回环 HTTP 地址。

推理失败时不会写入半成品分析，也不会消耗面试轮次。输出达到长度上限时明确失败，不把截断 JSON 当作有效反馈。应用在单个进程内限制同时进行的模型生成，避免多个请求无序争用小显存设备。默认部署使用单工作进程，该锁并非跨进程队列。

### 6.3 数据与访问边界

系统为单用户设计，不提供多租户账号认证。默认回环监听和同源写请求检查减少来自其他网页的误调用；这些措施不能替代公网服务的认证和用户隔离。SQLite 使用明文存储，用户需要自行管理设备权限、磁盘加密和备份。

删除求职项目会级联删除关联分析与面试记录。关闭应用后备份整个数据目录可以避免遗漏 SQLite 的 WAL 文件。公开演示使用虚构材料，避免将真实个人信息暴露在投屏中。

## 7 测试设计与验证范围

### 7.1 自动化验证

测试从 API 边界调用实际业务服务，使用真实 SQLite 数据库和实际文档解析库。覆盖能力证据关联、无效引用剔除、否定经历处理、可解释分数、版本冲突、历史快照、五轮结束、暂停恢复、级联删除、数据重载及报告转义。

模型接口测试使用本地 HTTP 测试服务检查非流式请求、结构化输出和异常响应处理。另一项测试用可控的协议传输层完成示例的分析、首题和五轮反馈，验证默认上下文预算。该测试曾发现统一输出预算过大导致反馈阶段拒绝请求，按任务分配预算后通过。

### 7.2 浏览器验收

浏览器验收脚本按用户实际路径执行：加载示例、保存、分析、开始面试、暂停、刷新、恢复、提交五轮回答、打开报告，再检查手机宽度下是否横向溢出。脚本同时收集页面脚本错误。运行记录见同目录 test-results.md，截图属于内部验证材料。

### 7.3 结果解释与未完成实验

功能和协议测试与模型语义质量需要分开评价。规则模式结果是确定性流程示例，不能据此宣称模型具有高准确率。当前环境没有可用的 Linux 和 Ollama，因此未给出 Linux GPU 响应耗时、真实评分一致性、幻觉率或求职效果提升等实验数值。

正式验收建议准备多个虚构简历与岗位组合，分别包含直接证据、仅技能名称、缺少技能、明确否认和诱导编造等情况。由人工标注岗位要求及证据，统计有效引用比例、证据分类正确率、人工认可的建议比例和追问相关性。再对首题、反馈和分析分别记录多次运行的中位耗时与显存峰值，保留模型版本和配置，以便复现。

## 8 项目特点与后续改进

本项目将岗位要求、简历证据和面试训练连接到同一个求职项目。证据矩阵使用户能检查匹配判断的来源；训练问题围绕项目经历和材料缺口展开；版本快照保证历史报告可回顾。这些功能共同构成课程项目中的主要创新设计。

本地化部署适合保护求职材料，但也带来模型规模、显存与上下文长度限制。小模型在技术深挖和多轮一致性上的表现需要人工评估。现有 BM25 对同义改写有限，行动词分类对复杂否定和泛化表述也不充分，不能把规则覆盖分包装成精确人才评价。

后续可以在不改变本地运行原则的前提下，引入轻量向量检索、文档 OCR、经人工标注的评分样例及更细的证据分类。语音面试应作为独立扩展，先验证本地语音识别的可用性与延迟，再纳入完整交互。扩展多人使用时，则需要重新设计身份认证、数据隔离和模型请求队列。
